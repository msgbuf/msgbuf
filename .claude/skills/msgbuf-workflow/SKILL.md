# The msgbuf working method

This skill is the meta-knowledge of how a session on this repository should run. It complements,
never duplicates, `CLAUDE.md` (build facts, architecture, gotchas) and `README.md` (the public
documentation of the `.proto` syntax, options and targets). Read both first. The GitHub issue
tracker at `msgbuf/msgbuf` **is** the work queue; `CHANGELOG.md` is the record of what shipped.

## 1. The operating loop

Work is a pipeline, not a pile:

1. **Intake**: user reports (chat or GitHub issues) and the open issues at `msgbuf/msgbuf`
   (`gh issue list -R msgbuf/msgbuf`). Bugs outrank queued features; a generator crash or
   uncompilable generated code outranks everything. Triage every new issue with a diagnosis
   comment *before* fixing. Labels are the GitHub defaults (`bug`, `enhancement`, `documentation`, …).
2. **Reproduce before dispatching.** Almost every report reduces to a `.proto` file. Write it,
   run the built generator on it in a scratch directory, and compile or run the output:

   ```bash
   J=$(ls $PWD/de.haumacher.msgbuf.generator/target/msgbuf-generator-*-full.jar)
   java -jar $J -out <scratch>/out <scratch>/repro.proto      # add -ts <dir> for the TypeScript target
   ```

   Know whether the problem is in the parser, the resolution/specialization stage, ID synthesis or
   one code generator (§ "Generator Pipeline" in CLAUDE.md), and whether it is a real bug, an
   already-fixed one, or your own probe error before an agent burns tokens. If the main tree is
   agent-owned, reproduce in a git worktree (`git worktree add --detach <scratch>/repro main`),
   never in the live tree.
3. **Dispatch** one sub-agent per coherent package (§2), or do it yourself when the package is
   small. msgbuf has one toolchain and one reactor, so parallel work needs separate worktrees (§3).
4. **Review with a novel probe** (§4). Non-negotiable.
5. **Gate** (§5), **commit and open or update the PR** (§6), close the issue with the fixing
   commit or PR plus a summary comment naming the regression test.
6. **Before finishing: `gh issue list -R msgbuf/msgbuf`.** Anything you find and defer becomes an
   issue (like #16–#21, found while building the TypeScript target), so a crashed session loses
   nothing.

Track packages with TaskCreate/TaskUpdate; keep statuses honest (in_progress on dispatch,
completed only after the commit is pushed).

## 2. Agent briefs — what makes them work

Use Opus for generator and runtime packages; Sonnet only for mechanical chores (regenerating,
README tables). Run in background; you'll be notified. A good brief contains, in order:

- **Grounding**: "Read CLAUDE.md and README.md. Study <the specific generator classes, the
  specific test `.proto` files and tests that are the behavioral contract>." Name the module
  (`de.haumacher.msgbuf` runtime, `de.haumacher.msgbuf.generator`, the Maven plugin) and whether
  `ast/proto.proto` or `parser/protobuf.jj` is in scope — both have regeneration consequences (§5).
- **The task as design intent**, with the load-bearing decisions already made: what the wire
  format carries, what the generated API looks like, which options (`NoInterfaces`, `NoJson`,
  `SharedGraph`, …) the change must respect, what the generator rejects with an error instead of
  emitting broken code. Quote the user's own words where they designed the feature.
- **User fixtures embedded verbatim**: the `.proto` from the report, the JSON the user expects, the
  compiler error they got. They become the regression test.
- **Explicit acceptance tests**: which test package under `src/test/java/test/` gets the new
  `.proto` and the JUnit 3 test (`extends TestCase`, see CLAUDE.md); JSON/binary/XML round-trips
  (write → read → equal) for every format the options leave enabled; exact expected JSON strings
  where the format is the point.
- **The build discipline block** (the point is not wasting runs, not avoiding them):
  - The edit loop runs the **owning module's targeted test**:
    `mvn -q -pl de.haumacher.msgbuf.generator -am test -Dtest=TestHierarchy -Dsurefire.failIfNoSpecifiedTests=false`.
    `-am` is needed unless the current `msgbuf-api` SNAPSHOT is installed in `~/.m2`.
  - A generator change is not tested until the checked-in test sources are regenerated (§5) —
    they are compiled from the repository, not generated by the build.
  - The full `mvn clean install` runs at the end, before the report. A run whose inputs did not
    change is not repeated "to be sure". Batch independent lookups in one call.
- **The standing rules block**: ALL existing tests green; never hand-edit generated code
  (regenerate it: test sources, the AST classes from `proto.proto`, the JavaCC parser);
  generated code and `msgbuf-api` stay GWT-compatible (no `java.io` Reader/Writer, Java language
  level of the root pom); do NOT commit; **nothing half-done — cut whole items only and report
  every cut**; a new generator error message names the file, the definition and the fix.
- **Ask for a report**: mechanism chosen and why, alternatives rejected, cuts, which checked-in
  generated files changed and why, test count before/after. A vague report predicts a vague delivery.

**Reworks go back to the same agent** via SendMessage with the failing probe and the demand:
*fix it generally, not to the probe*. If several rework rounds fail, question the architecture,
not the tests.

**Stalled agents**: if a background agent's transcript goes quiet, check for a running `mvn` or
`java` process first (a long build is not a stall), then nudge-resume via SendMessage ("Resume
exactly where you left off: <last visible step>"). If it stays frozen, take the remainder over;
its uncommitted work is usually further along than its last message suggests (`git status`, run
its tests before redoing anything).

**Crash recovery**: the crashed session's transcript is
`~/.claude/projects/-home-haui-devel-msgbuf/<session-id>.jsonl`, sub-agent transcripts are in
`<session-id>/subagents/`. Pull the last `Agent` tool_use out of the session transcript (that is the
brief, verbatim), check the tree (`git status`, `mvn -q compile`), and re-dispatch with a resume
preamble stating what exists and what compiles. Check `gh issue list` — reports filed during the
crash are untriaged.

## 3. Concurrency — the rules

- **Never let two agents edit the same file.** When parallelizing, write an explicit FILE BOUNDARY
  paragraph into *both* briefs ("do not touch X, Y, Z; if you must, STOP and report").
- **Shared hot spots have one owner per round**: `MessageGenerator.java` (most features touch it),
  `ast/proto.proto` (regenerates the AST every generator class uses), `parser/protobuf.jj`
  (regenerates the parser), and the checked-in test sources (a regeneration rewrites many files).
- **Concurrent Maven runs in one tree collide** on `target/` and on the `~/.m2` install of the
  same SNAPSHOT. A second agent gets its own worktree (`git worktree add -b <branch>
  <scratch>/wt-x main`, run from this repo) and uses `mvn verify`, never `install`, so it cannot
  overwrite the artifacts the main tree builds against.
- A commit made while an agent has uncommitted work in the tree must be **selective**
  (`git add <files>`).
- **A merge is not gated by the commits it merges.** Run the full gate (§5) on the merged tree —
  generated code and generator changes are exactly where merges break.

## 4. The probe review (the quality mechanism)

After a delivery reports done and before committing: **write a `.proto` the agent never saw**,
composing the new feature with existing ones: inheritance three levels deep with an abstract
intermediate, nested messages and enums, cross-file `import` and `extends`, `@Nullable`,
`repeated` and `map` of the new construct, reserved-word names in backticks, and the option
matrix (`NoInterfaces`, `NoJson`/`NoBinary`/`NoXml`, `NoReflection`, `NoListener`, `NoVisitor`,
`SharedGraph`, `OpenWorld`). Generate, compile, round-trip. Good probes ask "is the mechanism
general?" not "does the happy path work?". Keep passing probes as permanent test packages.

**Expect your own probes to be wrong first.** The traps seen so far:

- **The generator derives its output root from the `package` declaration** when `-out` is missing:
  the test protos live in `test/<x>/` but declare `package test.<x>.data;`, so running the jar on
  them without `-out` writes a stray `src/test/test/` tree. Always pass `-out`.
- **A run with `-Dmsgbuf.ts.update=true` is not a test run** — it rewrites the TypeScript golden
  files and then passes by construction. Rerun without the flag, and review the golden diff.
- **`mvn -pl de.haumacher.msgbuf.generator` alone fails to resolve `msgbuf-api:…-SNAPSHOT`** unless it
  is installed — use `-am`, and then `-Dsurefire.failIfNoSpecifiedTests=false` with `-Dtest=…`.
- **Stale jar**: `target/msgbuf-generator-*-full.jar` is whatever the last `install`/`package` built,
  possibly on another branch. Rebuild before probing a change.
- **A green unit build does not cover the plugin integration test**: `-Prun-its` runs it, and
  `simple-it` is the archetype template calling a non-existent `touch` goal (#18) — it fails on
  `main` too. Report it as known, don't chase it.
- **CLAUDE.md is not always right about the wire format**: polymorphic values are written as
  `[typeId, {fields}]` (a two-element array whose second element is the object), and only when the
  hierarchy root is abstract; references to a concrete type use `writeContent()` without a tag.
  Check `MessageGenerator` (`writeTo`, `isMonomorphicReferenceToTypeInPolymorphicHierarchy`)
  before asserting a format.
- **`gh pr view <n>` / `gh pr edit <n>` fail** with a GraphQL "Projects (classic) is being
  deprecated" error. Use `gh pr view <n> --json …` for reading and `gh api -X PATCH
  repos/msgbuf/msgbuf/pulls/<n> -F body=@file` for editing.
- **`gh pr checkout` names the local branch differently** from the PR head, so a plain `git push`
  is refused. Push with `git push origin HEAD:<headRefName>`.
- **A push can be rejected with a transient 403** ("Permission to msgbuf/msgbuf.git denied"). Report
  it; on the user's request, retry once before suspecting credentials.
- **The Bash tool resets its working directory between calls.** Use absolute paths; never
  `git add -A` after a relative `cd`.

When a probe legitimately fails: send it back (§2). Small, deeper defects found on the way get
fixed with a regression test; unrelated ones become issues. Two classics to stay paranoid about:
generated code that does not compile for some option combination, and a silent change of the wire
format (§7).

## 5. The verification gate (before every commit)

```bash
mvn clean install                       # api → generator → plugin, all unit tests

# If generator output changed: regenerate every checked-in test source and review the diff.
J=$(ls $PWD/de.haumacher.msgbuf.generator/target/msgbuf-generator-*-full.jar)   # absolute, before the cd
cd de.haumacher.msgbuf.generator
for p in $(find src/test/java -name '*.proto'); do java -jar $J -out src/test/java $p; done
git status --short                      # every changed file must be explained by the change
cd .. && mvn clean install              # the regenerated sources compile and pass
```

- **The checked-in generated test sources are golden files.** On `main`, regenerating them yields
  zero diff. The loop prints `ERROR: Map types not supported in XML: …` (five times) and a
  `Duplicate index '1' for 'RUNNING' and 'STARTED'` notice for the existing test protos — expected,
  not a failure. After a generator change, the diff of `src/test/java/test/**` *is* the review of the
  generated code: an unexplained change is a regression.
- **AST change** (`ast/proto.proto`): regenerate the AST classes with the previous generator
  (`java -jar $J -out src/main/java src/main/java/de/haumacher/msgbuf/generator/ast/proto.proto`),
  then rebuild. The build does not do this for you (#23; CLAUDE.md still claims otherwise).
- **Grammar change** (`parser/protobuf.jj`, next to the parser sources): the JavaCC plugin
  regenerates the parser into `src/main/java` during the build; the regenerated parser files are
  checked in and ride the same commit.
- **TypeScript target**: `TestTypeScriptGenerator` compares against
  `src/test/resources/ts/expected`; update with `-Dmsgbuf.ts.update=true`, then review the diff and
  rerun without the flag. Type-check the golden files plus a usage file with `@ts-expect-error`
  negative cases in the scratchpad:
  `npx -y -p typescript tsc --strict --noEmit --isolatedModules --verbatimModuleSyntax --moduleResolution bundler --module esnext --target es2020 <files>`.
- **Maven plugin changes**: also run `mvn install -Prun-its -pl msgbuf-generator-maven-plugin`
  (known failure #18 until fixed).
- The Eclipse plugin (`de.haumacher.msgbuf.eclipse`, `de.haumacher.msgbuf.feature`) is not in
  the reactor; changes there need a separate Eclipse/PDE build and are rare.

All green or no commit. Never trust a green result from a tree with uncommitted foreign edits;
check `git status` first. When reporting, give the numbers (tests per module) and say what was
*not* run — the user asks.

## 6. Branches, commits, PRs, releases

- **Issue work goes through a branch and a PR** (`feature/issue-<n>-<slug>`, `fix/issue-<n>-<slug>`
  in `msgbuf/msgbuf`, as for #12–#14), `Closes #<n>` in the PR body. Small doc and chore fixes
  may go straight to `main` when the user says so. External contributions arrive as PRs from forks.
- **House style**: an imperative one-line title stating the change, then a paragraph of the why
  (never a bullet changelog), ending with the Co-Authored-By line from the harness rules.
  Regenerated files ride the same commit as the change that produced them.
- **`CHANGELOG.md`**: every user-visible change gets an entry under the next version (the current
  SNAPSHOT), in the existing sections (New Features, Bug Fixes). README documents every new
  syntax element, option and generator switch.
- **PR descriptions** stay true to the branch: when a follow-up commit changes behavior, update the
  description in the same step (§4 for the `gh` workaround).
- **The agents don't commit; you do**, after review. Pushing and force-pushing a shared branch are
  the user's call; a history rewrite of a PR branch others may have checked out needs explicit consent.
- **Releases are the user's**: `mvn release:clean release:prepare` pushes a `msgbuf-api-<version>`
  tag, and the tag push runs `.github/workflows/release.yml`, which deploys to Maven Central
  (HOWTO-RELEASE.md). Never run `release:*`, never push a `msgbuf-api-*` tag, never edit the
  version numbers the release plugin manages.

## 7. Wire-format and generated-code doctrines (enforce in every brief and review)

- **The wire formats are a contract with deployed peers.** JSON, binary and XML written by one
  msgbuf version are read by another (TopLogic servers and clients, Dart and TypeScript consumers).
  A change in what a generated writer emits is a breaking change: it needs an explicit decision,
  a README and CHANGELOG note, and readers that still accept the old form. Readers stay lenient
  (missing properties take defaults).
- **All targets describe one format.** The Java writer is the reference; the Dart and TypeScript
  targets must describe exactly what it writes (property names = `*__PROP` constants, enum
  protocol names, nullable fields omitted, polymorphic tuples). Verify against the Java generator,
  not against the docs.
- **Generated code must compile for every option combination** and stay GWT-compatible: no
  `java.io` Reader/Writer in `msgbuf-api` or generated code, no features beyond the language level
  of the root pom, no dependencies beyond `msgbuf-api`.
- **The generator rejects, it doesn't emit garbage.** Invalid input gets an error naming the
  file and definition (see #16, #21 for the failure mode to avoid: a crash or uncompilable output).
- **Names are honest.** Generated and internal names say what a thing is (the TypeScript types are
  `…Json` because they describe the JSON format, not the data). The user will notice a name that
  claims more than it delivers.
- **Licenses**: `msgbuf-api` is Apache-2.0, the generator GPL-3.0-or-later, generated code is
  unencumbered. Generated code may only depend on `msgbuf-api`; don't copy generator code into
  templates of generated code.
- **Everything generic**: a fix shaped like the bug report is not done. It must hold for nested,
  inherited, cross-file and option-varied variants of the reported case (the probe of §4).

## 8. Working with this user

The user is the author of msgbuf, an expert in Java, code generation and software architecture,
and a main downstream consumer (TopLogic). They review sharply and ask for evidence: "did you run
the tests???" is answered with the command, the counts per module, and what was not run — never
with an unqualified "yes". Their design remarks are usually complete (e.g. naming the generated
TypeScript types after what they are); restate the design crisply, adopt it, and credit it in the
commit message. Answer questions with the mechanism first, then the recommendation. When they
overrule a suggestion ("keep one PR"), follow it without relitigating.
